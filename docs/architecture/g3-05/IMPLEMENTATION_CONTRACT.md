## 1. 목적과 우선순위

이 문서는 DOC-11과 TEC-04의 구현용 요약본이다. Claude Code 등 개발 도구가 구현 전에 반드시 확인해야 할 기술 계약을 정의한다. 충돌 시 적용 순서는 다음과 같다.

1. 승인된 계약서와 발주자 서면 결정
2. DOC-07 요구사항정의서 v0.4
3. DOC-10 화면·UI/UX 설계서 v0.1
4. DOC-11 시스템·DB·API·보안 설계서 v0.1
5. TEC-03 Supabase RLS·권한표 v0.2
6. TEC-04 API·데이터 계약서 v0.1
7. 이 구현 계약

## 2. 변경 금지선

- 원본 저장소에는 commit, push, PR, tag를 만들지 않는다.
- 원본 Vercel에는 preview와 production 배포를 하지 않는다.
- 원본 Supabase에는 INSERT, UPDATE, DELETE, DDL, migration, RPC를 실행하지 않는다.
- 신규 환경의 키·토큰·서비스 역할 키는 코드, 로그, 문서, 화면에 남기지 않는다.
- 신규 Supabase 변경은 G3 승인 뒤 `supabase/migrations`의 migration으로만 수행한다.
- 104만 건 데이터는 migration SQL에 포함하지 않고 재개 가능한 배치 적재 절차로 이관한다.

## 4. 스키마 경계

Data API에 노출되는 스키마는 `public` 하나로 제한한다. 원천 적재·검역·운영·감사 데이터는 API 비노출 스키마에 둔다.

### 4.1 공개 조회 마스터

| 객체 | 키 | 공개 범위 | 쓰기 주체 |
|---|---|---|---|
| `public.facilities` | `mgt_no` | 업체명, 상태, 공개 주소, 전화, 지역, 좌표, HACCP 요약 | 배치·서비스 역할 |
| `public.products` | `report_no` | 제품명, 유형, 제조사명, 제조시설 키, 원재료명, 소비기한 일수, 신고·수정일 | 배치·서비스 역할 |
| `public.recipes` | `recipe_id` | 제목, 분류, 인분, 설명 요약 | 배치·서비스 역할 |
| `public.ingredients` | `ingredient_id` | 표준명, 정규화명, 공개 별칭 | 배치·서비스 역할 |
| `public.recipe_ingredients` | `id` | 레시피·식재료 키, 원문 용량·단위, 정렬순서 | 배치·서비스 역할 |
| `public.haccp_certifications` | `id` | 공개 인증번호·품목·기간·시설 키 | 배치·서비스 역할 |
| `public.sales_suspensions` | `id` | 공개 처분 요약·기간·시설 키 | 배치·서비스 역할 |

모든 객체는 RLS를 활성화한다. `anon`과 `authenticated`에는 안전한 열의 SELECT만 허용하고 INSERT·UPDATE·DELETE 권한을 주지 않는다.

### 4.2 회원 소유 객체

| 객체 | 소유권 | 주요 자식 보호 |
|---|---|---|
| `public.profiles` | `id = auth.uid()` | 역할 값은 클라이언트 변경 금지 |
| `public.saved_items` | `user_id = auth.uid()` | 대상 유형·대상 ID 유효성 검증 |
| `public.projects` | `user_id = auth.uid()` | 프로젝트 자식은 부모 소유권으로 보호 |
| `public.project_events` | 부모 프로젝트 소유권 | 직접 URL·직접 API 접근도 차단 |
| `public.candidate_runs` | 부모 프로젝트 소유권 | 입력·규칙버전·상태·실행시각 기록 |
| `public.candidate_results` | 부모 실행 소유권 | 근거·점수·주의사항 포함 |
| `public.label_checks` | 부모 프로젝트 소유권 | OCR·직접입력·규칙·설명 결과 연결 |

소유자 정책은 `USING`과 `WITH CHECK`를 모두 사용한다. UPDATE 정책에는 SELECT 정책이 반드시 존재해야 하며, `user_id` 변경은 허용하지 않는다.

### 4.3 공동구매·문의 객체

| 객체 | 공개/비공개 원칙 |
|---|---|
| `public.group_buys` | 공개·게시 상태의 본문만 비회원 조회 가능. 작성자와 운영자만 수정·숨김 가능 |

### 4.4 API 비노출 운영 객체

`ops`와 `audit` 스키마는 Data API에 노출하지 않는다.

- `ops.data_snapshots`: 원천명, 추출시각, 파일 해시, 기준 건수
- `ops.ingest_runs`: 적재 실행, 배치 범위, 성공·실패·검역 건수, 재개 토큰
- `ops.quarantine_rows`: 원천 키, 오류 코드, 원문 해시, 정정 상태
- `ops.external_call_events`: 공급자, 기능, 성공 여부, 지연시간, 비용 단위, trace ID. 입력 본문·OCR 전문 금지
- `ops.external_call_daily`: 일별 호출량·실패율·차단 상태
- `audit.operator_actions`: 운영자 조치 대상·사유·시각. 비밀값과 입력 전문 금지

## 5. 공개 검색 계약

| 자원 | 기본 정렬 | 커서 키 | 1회 한도 |
|---|---|---|---:|
| 시설 | 업체명 오름차순 | `name, mgt_no` | 50 |
| 제품 | 신고일 내림차순, 신고번호 오름차순 | `reported_at, report_no` | 50 |
| 레시피 | 제목 오름차순 | `title, recipe_id` | 50 |
| 식재료 | 정규화명 오름차순 | `normalized_name, ingredient_id` | 50 |

- 커서는 서버가 만든 불투명 문자열로 전달한다.
- 동일 입력·동일 스냅샷에서 중복·누락 없는 페이지 경계를 보장한다.
- 정확한 전체 건수는 기본 응답에서 계산하지 않는다. 검증된 스냅샷 건수 또는 추정치를 별도 필드로 표시한다.
- 검색어는 길이와 허용 문자를 검증하고, 정렬 열은 허용 목록에서만 선택한다.
- 제품 검색은 신고번호, 제품명, 유형, 제조사명, 제조시설 키를 지원한다.
- 공개 검색 구현은 서버 함수 또는 Route Handler를 경유하며 브라우저에 서비스 역할 키를 전달하지 않는다.

권장 인덱스는 정렬·관계 키용 B-tree와 한글 부분검색용 `pg_trgm` GIN이다. 실제 인덱스는 적재 후 `EXPLAIN (ANALYZE, BUFFERS)`와 저장용량을 확인해 확정한다.

## 6. 애플리케이션 API 원칙

| 구분 | 방식 | 비고 |
|---|---|---|
| 공개 검색 | `GET /api/search/{resource}` | 비회원 가능, 속도제한·입력검증 |
| 상세 조회 | `GET /api/{resource}/{id}` | 안전한 공개 열만 반환 |
| 저장·프로젝트 | 서버 Action 또는 `/api/me/*` | 세션과 RLS 이중 확인 |
| 후보 실행 | `POST /api/projects/{id}/candidate-runs` | 규칙버전·입력해시·결과 계보 기록 |
| 표시 점검 | `POST /api/projects/{id}/label-checks` | OCR 또는 직접입력, 서버 전용 외부 호출 |
| 공동구매 | `/api/group-buys/*` | 공개 본문과 연락처 분리 |
| 비공개 문의 | `/api/inquiries/*` | 문의자·운영자 전용 |
| 운영 | `/api/admin/*` | 서버 검증 운영자만 접근 |

성공 응답은 `data`, `meta`, `traceId`를 사용한다. 실패 응답은 아래 형식을 고정한다.

```json
{
  "error": {
    "code": "FG_AUTH_REQUIRED",
    "message": "로그인이 필요합니다.",
    "retryable": false,
    "fallback": "login"
  },
  "traceId": "01J..."
}
```

공개 오류에는 SQL, 테이블명, 공급자 키, 내부 URL, 입력 전문, 스택 추적을 포함하지 않는다.

## 8. OCR·LLM·표시 점검

- 이미지 업로드는 인증 사용자만 가능하며 비공개 `label-inputs` 버킷을 사용한다.
- 저장 경로는 `{auth.uid()}/{label_check_id}/{uuid}`로 고정한다.
- MIME, 확장자, 파일 서명, 해상도, 크기 상한을 서버에서 확인한다.
- OCR과 LLM 키는 서버 환경변수에서만 읽는다.
- OCR 성공 뒤 원본 이미지는 즉시 삭제하고, 실패·중단 파일은 최대 24시간 내 삭제한다.
- OCR 실패 시 사용자가 텍스트를 직접 입력·수정해 계속 진행할 수 있어야 한다.
- LLM은 규칙 결과를 설명하는 보조 수단이다. 법적 적합 여부를 단독 확정하지 않는다.
- 외부 호출이 중단되면 규칙 기반 결과와 참고 근거는 계속 제공한다.
- 일별 호출량·실패율·차단 여부는 기록하되 입력 본문과 이미지 내용은 기록하지 않는다.

## 9. 보존·삭제 기준

| 데이터 | 기본 보존 | 삭제 원칙 |
|---|---|---|
| OCR 원본 이미지 | 성공 시 즉시, 그 외 최대 24시간 | 정기 정리 작업과 수동 재처리 경로 |
| 표시 점검 결과 | 사용자 삭제 또는 프로젝트 삭제 전 | 계정 삭제 시 함께 삭제 |
| 저장목록·프로젝트 | 사용자 삭제 전 | 30일 복구대기 후 영구삭제를 목표로 구현 |
| 공동구매 게시물 | 사용자 삭제 또는 운영 조치 전 | 연락처는 본문과 별도 삭제 가능 |
| 종료된 비공개 문의 | 1년 | 법무·개인정보 검토 후 파기 또는 비식별화 |
| 운영 호출·감사 기록 | 180일 | 입력 전문 없이 통계·조치 근거만 보존 |

개인정보 보존기간은 서비스 공개 전에 개인정보 처리방침·법무 검토 결과로 확정하며, 더 긴 기간이 필요하면 별도 승인한다.

## 10. Migration과 적재 순서

1. `0000_extensions_schemas_types`: 확장, 비노출 스키마, enum, 안전한 헬퍼
2. `0010_public_masters`: 시설·제품·레시피·식재료·관계 테이블
3. `0020_public_indexes`: 관계·정렬·검색 인덱스
4. `0030_identity_projects`: 프로필·저장목록·프로젝트
5. `0040_candidate_label`: 후보 실행·결과·표시 점검·발견사항
6. `0050_groupbuy_inquiry`: 공동구매·참여·연락처·신고·문의
7. `0060_ops_audit`: 스냅샷·적재·검역·외부호출·감사
8. `0070_rls_grants`: 모든 RLS·권한·운영자 헬퍼
9. `0080_storage`: 비공개 버킷과 소유경로 정책
10. `0090_functions_views`: 승인된 함수·조회계층
11. `0100_smoke_config`: 비밀값 없는 초기 설정과 검증 쿼리

대량 데이터는 schema migration 뒤 별도 적재기로 처리한다. 각 배치는 스냅샷 ID, 범위, 원천 건수, 적재 건수, 중복 건수, 검역 건수, 해시, 재개 토큰을 기록한다.

## 11. 용량과 성능 기준

- 신규 프로젝트의 DB 한도는 8GB 기준으로 관리한다.
- 첫 전량 적재 후 테이블·인덱스 합계 2GB 이내를 목표로 측정한다. 이는 예측치가 아니라 검증 목표다.
- 4GB 도달 시 인덱스와 보존정책을 검토하고, 6GB 도달 시 추가 적재를 중지해 승인받는다.
- 원문 blob, OCR 이미지, 중복 원천행, 전체 감사 본문을 검색 테이블에 저장하지 않는다.
- 제품 상세와 검색에 필요한 열만 `public.products`에 적재한다.
- 공개 검색의 P95 목표는 정상 부하에서 2초 이내이며, 실제 기준은 TEC-08 성능시험계획에서 확정한다.

## 12. 배포·복구 게이트

- 로컬 `supabase db reset`과 정적 SQL 검사를 통과하기 전 원격 migration 금지
- 신규 프로젝트 ref가 `glczrbadvfgmblmkpgfj`인지 이중 확인
- 원격 적용 전 스키마 덤프·설정 스냅샷·기준 건수 기록
- migration 적용 담당자 한 명, 적용 로그와 migration 목록 보존
- 적용 후 모든 public 객체의 RLS 활성, 권한, 함수 search path, Storage 정책 검사
- 회원 2계정과 운영자 1계정으로 직접 URL·직접 API·자식행 접근 음성시험
- 데이터 적재는 샘플, 1%, 10%, 전량 단계로 진행하고 각 단계에서 건수·중복·결측·용량 확인
- 사용자 데이터가 생기기 전에는 신규 빈 프로젝트 재생성이 최후 복구수단이며, 사용자 데이터 발생 뒤에는 전진 수정 migration과 백업 복구를 우선한다.

## 13. 필수 음성시험

- 비회원은 개인 저장목록·프로젝트·문의·연락처를 읽지 못한다.
- A회원은 B회원의 저장목록·프로젝트·후보결과·표시점검을 읽거나 바꾸지 못한다.
- 자식 테이블 ID를 알아도 부모 소유자가 아니면 접근할 수 없다.
- 일반 회원은 운영 API·운영 역할·감사이력을 사용할 수 없다.
- 공동구매 비공개 연락처는 공개 목록·상세·검색 응답에 포함되지 않는다.
- 서비스 역할 키와 외부 API 키는 브라우저 번들·오류·로그에 노출되지 않는다.
- 제품 전량 적재 후 신고번호 중복·누락과 페이지 경계 중복·누락이 없다.
- OCR 중단 시 직접입력, LLM 중단 시 규칙 결과 대체경로가 동작한다.
