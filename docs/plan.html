1. 기획 요약

푸드그라운드는 공공데이터(식품제조시설 등록·생산이력·HACCP 인증·판매중지)를 수집해 "조회 · 저장 · 업데이트 알림" 3개 축만 제공하는 경량 플랫폼으로 정의한다. 채팅·결제·리뷰 같은 양방향 기능은 의도적으로 배제하고, 컨택은 mailto: / tel: 링크로 종결한다.

무엇을 한다

  • 특정 조건(업종·지역·HACCP 여부 등)으로 식품제조시설 검색
  • 업체 상세(생산이력 · HACCP · 판매중지 이력) 카드로 확인
  • 메일·전화 링크로 외부 컨택 유도 (플랫폼 내부 채팅 없음)
  • 관심업체 저장 → 변경사항 발생 시 알림 센터에 노출

무엇을 하지 않는다

  • 실시간 채팅 / 실시간 지도 / 결제 / 계약 체결
  • 리뷰 · 평점 · 추천 랭킹 (법적·편향 리스크)
  • 공공 API의 런타임 직접 호출 (TTI·RAS 불안정 요인)
  • 사용자 업로드 대용량 미디어 (TTI 저해 요인)
핵심 설계 명제. 모든 화면은 "DB에 이미 있는 데이터만 보여주고, 외부 호출은 백그라운드 배치로 분리"한다. → 사용자 요청 경로에서 외부 API 지연·장애가 배제되므로 TTI와 Server RAS가 구조적으로 보호된다.

2. 목표 성능지표 (TTI · Server RAS)

지표정의계획서 목표내부 버퍼 목표평가기관
TTI
Time to Interactive		 ATF(스크롤 없이 보이는 영역)가 완전 로드되어 사용자가 상호작용 가능해지는 시간 ≤ 1,000 ms ≤ 800 ms TTA 소프트웨어 시험인증 연구소
Server RAS
Reliability · Availability · Serviceability		 1초 간격으로 헬스체크를 5시간 보냈을 때, 5분 연속 무응답이 없는 상태 정상 (5시간 연속 응답) 6시간 무중단 검증 TTA
달성 실패 시 리스크. 재시험 비용은 재청구되며, 지표 비중은 각 5%지만 "지표 정상" 판정 여부가 전체 TIPS 평가 서술에 영향. 따라서 의뢰 전 내부 시뮬레이션을 반드시 통과한 뒤에만 TTA에 접수한다.

사용자가 제안한 원안을 성능지표 관점에서 재평가하여 유지 / 추가 / 삭제 / 간소화로 분류한다.

기능판정근거 · 변경 내용

데이터 갱신 주기 안내 · 경고문 유지 각 상세 카드 하단에 최종 동기화 일시와 "실제와 다를 수 있으니 사전 확인 권장" 경고문 고정 노출.
경량 로그인 (이메일 매직링크 또는 카카오) 추가 NEW 관심업체·알림이 기기 간 동기화되려면 필요. 단, 비로그인 열람은 허용(TTI 경로에 인증 미포함).
검색 필터 (업종·지역·HACCP 여부·판매중지 이력) 추가 NEW 의뢰자가 "쓸 수 있는 업체"로 좁히는 핵심 UX. DB 인덱스로 O(ms) 응답 가능.

실시간 채팅 / 쪽지 / 1:1 문의 삭제 CUT WebSocket·큐 도입 시 RAS 복잡도 급증. mailto:로 종결 충분.
리뷰 · 평점 · 추천 랭킹 삭제 CUT 사업자 명예훼손 리스크 + UGC 모더레이션 비용. 공공데이터 기반 팩트만 노출.
결제 · 계약 체결 삭제 CUT v1 스코프 외. 결제 게이트웨이 장애는 곧 RAS 실패로 귀결.
실시간 지도 (Kakao/Naver Map SDK 풀뷰) 삭제 (대체) 상세에 Static Map 이미지 1장만 사용 (CDN 캐시 가능). TTI/JS 번들 영향 제거.
자동완성 검색 간소화 300ms debounce + 결과 10건 제한. 서버 페이로드 ≤ 20KB.

4. 정보 구조 & 주요 플로우

사이트맵. /healthz는 Server RAS 측정용 전용 엔드포인트로, UI 라우트와 분리해 경량 유지.

핵심 사용자 플로우

  1. 도착 → 검색. 의뢰자(일반인/제조시설)가 메인 진입 → 지역+업종 선택 → 결과 리스트. (서버는 DB만 조회)
  2. 업체 상세. 카드 클릭 → 상세(ISR 정적 페이지) → 생산이력·HACCP·판매중지·경고문 확인 → mailto: 클릭으로 플랫폼 이탈.
  3. 관심 저장. 비로그인은 localStorage에, 로그인은 서버 테이블에 저장. 저장 자체는 비동기(화면 블로킹 없음).
  4. 알림 수신. 주간/월간 배치가 변경 감지 → alerts 테이블에 행 추가 → 다음 방문 시 Bell 아이콘 배지 표시.

5. 와이어프레임 (5개 핵심 화면)

5-1. 메인 · 홈

메인. ATF에는 히어로 문구 + 검색바 + 필터 칩만 존재. 이미지/캐러셀 없음 → TTI 최적화.

5-2. 검색 결과 리스트

검색 결과. 좌측 필터는 쿼리 파라미터 기반 URL 상태. 무한 스크롤 대신 페이지네이션 → 이벤트 리스너 수 최소화.

5-3. 업체 상세

상세. ISR로 정적 생성(주기적 재생성). 이미지는 Static Map 1장만. 하단 경고문 고정 노출 규칙은 전 업체 공통.

5-4. 관심업체 관리

관심업체. 업데이트 있는 업체 앞에 주황 도트(빨강 대신 컬러블라인드 대응) 표시. 탭 전환은 클라이언트 필터.

5-5. 알림 센터

알림 센터. 읽음 처리는 서버 PATCH /alerts/:id/read 한 번. 실시간 소켓 없음 → RAS 복잡도 최소.

6. 데이터 동기화 · 저장 모델

공공 API 호출은 전적으로 백엔드 배치(cron)에서만 수행하며, 사용자 요청 경로에는 절대 포함되지 않는다. 사용자 화면은 항상 "자체 DB의 스냅샷"을 본다.

데이터셋주기동기화 방식저장 위치비고
식품제조시설 등록정보 초기 전량 → 이후 주 1회 증분 최초 full dump → 이후 변경분(추가/삭제) diff 적재 facility 테이블 + 전문검색 인덱스 영업등록번호를 PK로. 삭제는 soft delete.
제품 생산이력 월 1회 업체별 최근 N개월 호출 → upsert production_log (FK: facility) 상세 페이지 ISR 재생성 트리거
HACCP 인증현황 연 1회 전량 덤프 haccp_cert (FK: facility) 만료일 + 30일 이전부터 상세에 안내
판매중지 정보 주 1회 최근 N주 변경분 적재 sales_suspension (FK: facility) 알림 테이블 자동 파생

알림 생성 규칙

  • 관심업체 사용자 × (신규 생산이력 | HACCP 갱신 | 판매중지 신규) → alerts 레코드 1개 생성
  • 읽음 여부는 사용자별 플래그. 만료 90일 이후 자동 폐기.
  • 푸시 알림·이메일·SMS는 v1에서 제외 — 방문 시 Bell 배지로만 확인.
사용자 UI에 고정 노출되는 경고문
"본 정보는 공공데이터 기반 N주 주기 스냅샷입니다. 최근 1주 이내의 생산·중지 상태는 반영되지 않을 수 있으니, 계약·발주 전 반드시 해당 업체에 메일·전화로 확인해 주세요."

7. TTI ≤ 1,000ms 달성 전략

TTA는 ATF 기준 렌더링/상호작용 시간을 Lighthouse 등 자체 도구로 재측정한다. 따라서 "방문자가 가장 먼저 열 확률이 높은 페이지(메인·검색결과·업체상세)"를 정적에 가깝게 만들어야 한다.

렌더링 전략 (화면별)

화면전략이유
메인 /SSG (배포 시 프리렌더)동적 요소 없음 → 순수 정적
업체 상세 /b/:idISR (revalidate = 동기화 주기)데이터 갱신 빈도 낮음. CDN이 대부분 흡수
검색결과 /search?…SSR (엣지 캐시 60s)쿼리 파라미터 조합 발산 → SSG 불가, 그러나 동일 쿼리에 대한 캐시로 흡수
관심업체·알림클라이언트 렌더 (인증 필요)TTA 측정 URL에서 제외 → TTI 영향 없음

자산 · 스크립트 체크리스트

  • 초기 JS 번들 ≤ 150 KB (gzip). 라우트별 코드스플릿.
  • 이미지는 전 페이지 WebP + loading="lazy", 히어로 이외는 lazy 고정. 상세 Static Map은 CDN 캐시.
  • 폰트: 시스템 폰트를 기본 스택으로 사용. Pretendard 등은 서브셋 woff2 + font-display:swap.
  • Third-party 스크립트(분석·지도 SDK 등) 도입 금지. 계측은 자체 서버 로깅.
  • CSS 인라인 크리티컬 + 나머지 프리로드.
  • HTML 문서 ≤ 30 KB (gzip 전).

인프라

  • CDN: Cloudflare (서울 엣지) — 정적 자산은 100% 엣지 종결.
  • Origin 서버: 서울 리전. TLS는 HTTP/2 + TLS 1.3.
  • DB: PostgreSQL (읽기 전용 슬레이브 1대). 검색 인덱스(facility의 지역·업종·HACCP 여부) 사전 생성.
  • Redis: 세션 + 검색결과 페이지 캐시(TTL 60s).

내부 검증 프로토콜 (TTA 의뢰 전)

  1. lighthouse CLI로 메인·검색결과·업체상세 3개 URL을 각 5회 측정, 중앙값으로 평가.
  2. 측정 환경: Slow 4G (throttling 1.6Mbps/750ms RTT), 모바일 에뮬, Chrome 표준.
  3. 내부 버퍼 기준 TTI ≤ 800ms 모두 통과 시에만 TTA 접수.
  4. 실패 시 개선 순서: 이미지 → JS 번들 → 써드파티 → 서버 응답 시간 순.
원칙 재확인. 사용자 요청 경로에서 공공 API를 호출하지 않는다는 설계만으로도 TTI의 90% 이상은 사전 방어된다. 나머지 10%는 번들/이미지 최적화에서 확정한다.

8. Server RAS "정상" 달성 전략

측정 프로토콜은 1초 간격 HTTP 요청 × 5시간 = 18,000회이며, 5분 연속 무응답이 단 한 번이라도 발생하면 탈락이다. 장애 원인의 대부분은 (a) 배포 중 롤링 순간, (b) DB 커넥션 고갈, (c) 외부 API 지연 전파 이다. 이 세 가지를 구조적으로 제거한다.

헬스체크 엔드포인트 설계

  • 경로: GET /healthz
  • 처리: 원자적인 DB ping(SELECT 1, 타임아웃 500ms) → 실패 시 200이 아니라 503 반환.
  • 응답 페이로드: {"ok":true,"ts":<epoch>,"db":"up"} (≤ 100 byte)
  • 인증·세션·레이트리밋 미적용 → 라우트 복잡도 최소.
  • Next.js / Express 공통으로 가장 얕은 레이어에 마운트.

프로세스 · 배포 정책 (측정 기간)

  • TTA 의뢰 기간은 팀 캘린더에 "배포/점검 금지 freeze"로 등록.
  • 무중단 배포가 필요한 경우 blue-green + 헬스체크 통과 확인 후 트래픽 스위치.
  • Node/PM2 자동 재시작(--max-memory-restart 400M) + docker healthcheck.
  • cron 배치(데이터 동기화)는 측정 시간에 실행하지 않는다. lock 파일로 방지.

외부 의존성 격리

  • 공공데이터 API 실패는 사용자 경로에 절대 전파되지 않는다. 배치 레이어에서만 발생.
  • 검색결과 조회 시 DB 에러가 나면 Redis 캐시에 있던 직전 성공 응답을 반환(≤ 60초 stale) → 200 유지.
  • 상세 페이지는 ISR 정적 HTML → 오리진 DB가 잠깐 죽어도 CDN이 응답.

내부 5시간 시뮬레이션 스크립트

with OUT.open("w") as f:
    for i in range(DURATION_SEC):
        t0 = time.time()
        try:
            r = requests.get(URL, timeout=3)
            ok = (r.status_code == 200)
            row = {"t": datetime.datetime.utcnow().isoformat(), "code": r.status_code, "ms": int((time.time()-t0)*1000)}
        except Exception as e:
            ok = False
            row = {"t": datetime.datetime.utcnow().isoformat(), "code": "ERR", "msg": str(e)}
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
        fail_streak = 0 if ok else fail_streak + 1
        max_fail = max(max_fail, fail_streak)
        # 1초 간격 유지 (요청 소요시간 보정)
        elapsed = time.time() - t0
        if elapsed < 1.0: time.sleep(1.0 - elapsed)

# 통과 기준: 연속 5분(300초) 이상 실패 없음
print("max consecutive failures:", max_fail, "→", "PASS" if max_fail < 300 else "FAIL")

모니터링 · 증빙

  • 외부 감시: UptimeRobot 1분 간격 + StatusCake 1분 간격 이중화.
  • 내부 로그: winston + daily-rotate, 30일 보관. 오류율 임계치 초과 시 이메일 알림.
  • TTA 제출 시 첨부: ras_log.jsonl, 서버 아키텍처 다이어그램, 배포 freeze 캘린더 캡처.

9. 시스템 아키텍처 (경량 단일 스택)

단일 리전·단일 스택. 외부 의존 경로는 점선으로 완전히 격리되어 RAS 측정 리스크에서 제외된다.

주요 스택 선정 이유

  • Next.js — SSG/ISR/SSR을 한 프레임워크에서 전환 가능. TTI 전략과 직접 매칭.
  • PostgreSQL — 지역·업종·HACCP 등 조합 필터에 강한 B-tree + GIN 인덱스.
  • Redis — 세션 + 쿼리 결과 캐시(60s) + 배치 lock.
  • Cloudflare — 엣지 HTML/정적 자산 종결. 오리진 실패 시에도 캐시된 HTML 응답 가능.

10. 보안 · 개인정보 · 법적 고지

  • 공공데이터는 재배포 시 출처 명기. 푸터에 "출처: 식품의약품안전처 · 공공데이터포털" 고정.
  • 업체 연락처는 공공등록 정보 범위 내에서만 노출(사업자 전화/주소). 대표자 개인 휴대전화 등은 표시하지 않는다.
  • 이용자가 저장한 관심업체·알림은 개인정보 최소 수집 원칙 (이메일만).
  • 이용약관에 "본 서비스가 제공하는 정보는 스냅샷이며, 거래·계약은 사용자의 확인 책임" 명시.
