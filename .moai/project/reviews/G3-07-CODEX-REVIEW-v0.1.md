### B-02. 기존 분석 산출물의 실제 계약 반영

`food_pair_similarities.csv` 실제 6개 지표는 다음과 같다.

2. `재료구분_유사도`
3. `식품군_유사도`
4. `조리상태_유사도`

### B-03. 52.85% 의미와 계보 정정

`ingredient_matching.csv`의 23,806개 고유 입력명 분포는 다음과 같다.

| 매칭방법 | 건수 | 비율 |
|---|---:|---:|
| 완전일치 | 488 | 2.05% |
| 포함일치 | 11,764 | 49.42% |
| 철자유사 | 295 | 1.24% |
| 동의어 | 35 | 0.15% |
| 미매칭 | 11,224 | 47.15% |
| 합계 | 23,806 | 100.00% |

12,582/23,806 = 52.85%는 `완전일치율`이 아니라 전체 매칭 성공률이다. DB와 UI는 원본 매칭방법을 보존하고, 필요하면 `완전일치`와 `비정확 매칭`을 상위 표시범주로 추가한다. 미매칭을 부분일치로 표시하지 않는다.

### B-06. 공개 조회·민감필드 보안 정정

- 읽기 전용 원본 SQLite `facility` 테이블에는 `tel`과 `homepage`는 있지만 `email` 컬럼은 없다. 별도의 승인된 이메일 소스가 확인되기 전에는 mailto 수신자를 구성할 수 있다고 가정하지 않는다.
- 승인 이메일이 없을 때는 문의문안 복사를 기본 대안으로 제공하고, 공개 가능한 전화번호·홈페이지가 있을 때만 보조 연락정보로 표시한다. 별도 이메일 데이터가 확보되면 이용권한·공개범위·시설키 연결을 확인한 뒤 mailto를 활성화한다.
- 공개 검색 런타임에 service-role을 사용하지 않는다. server-side anon client와 RLS, 공개 전용 view 또는 컬럼 권한을 사용한다.
- RLS는 행 접근을 제어하며 컬럼 allowlist를 대신하지 않는다. 시설 이메일이 미확정인 동안 공개 객체에서 해당 컬럼을 제외한다.
- `data_lineage.source_path` 등 내부 계보정보는 공개 테이블에 두지 않고 private/internal 스키마에 둔다. 화면에는 승인된 기준일·버전만 공개한다.
- service-role은 승인된 migration·적재·관리 작업에만 제한하고 브라우저 번들과 공개 Route Handler 런타임에서 사용하지 않는다.

### B-07. 키·타입·연결관계 정정

- 제조시설 안정키는 감사에서 확인된 `mgt_no`를 우선 사용한다. 근거 없이 UUID로 교체하지 않는다.
- 대체 식품 ID는 실제 `기준식품ID`·`후보식품ID` 문자열 계약을 반영한다.
- 레시피 70,165·식재료 18,933 런타임 마스터와 분석 산출물의 69,406 레시피·686 표준식품 사이의 별도 계보와 crosswalk를 정의한다.
- 실제 원본 필드·키를 확인하기 전 DDL을 확정형으로 제시하지 않는다.

### B-08. 안전한 migration·rollback 정정

- `DISABLE ROW LEVEL SECURITY`는 rollback으로 사용하지 않는다.
- 공개권한 rollback은 grant 회수, 공개 view/version 전환 또는 직전 migration의 역방향 변경으로 설계한다.
- 운영성 테이블을 무조건 `TRUNCATE`하는 방식 대신 staging 격리, 트랜잭션, publish 버전 전환과 백업 복구를 사용한다.
- 고정 기준선 데이터는 `±1% 허용`이 아니라 정확 건수 또는 승인된 reject 사유·건수로 대조한다.

### B-09. QA 기준 정정

- `52.85% exact` 검사는 삭제하고 B-03의 매칭방법별 건수와 전체 매칭 성공률을 대조한다.
- 2초 P95, LCP 2.5초, 3초 등의 신규 수치는 계약 합격기준으로 추가하지 않는다. 진단 목표로 사용할 경우 실제값·병목·개선결과를 기록하며 DOC-07의 현재 웹 품질 측정 문구와 구분한다.
- 외부 시험기관, 과거 TIPS 동일수치 재달성, 100명 부하시험을 필수 인수기준으로 만들지 않는다.
